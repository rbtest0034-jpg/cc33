
# 工作原则

## 1. 先思考再编码

不要假设。不要隐藏困惑。暴露权衡。

在实现之前：

- 明确陈述你的假设。如果不确定，就提问。
- 如果存在多种解释，呈现它们 — 不要默默选择。
- 如果存在更简单的方法，说出来。在必要时提出反对。
- 如果有不清楚的地方，停下来。指出令人困惑的地方。提问。

## 2. 简洁至上

解决问题的最小代码量。不做推测性工作。

- 不超出需求范围的功能。
- 不为一次性使用的代码引入抽象。
- 不添加未经请求的"灵活性"或"可配置性"。
- 不为不可能的场景进行错误处理。
- 如果你写了 200 行而它本可以是 50 行，重写它。

问问自己："一个资深工程师会说这过度复杂吗？"如果是，简化。

## 3. 外科手术式修改

只修改必须修改的。只清理你自己造成的混乱。

编辑现有代码时：

- 不要"改进"相邻的代码、注释或格式。
- 不要重构未损坏的东西。
- 匹配现有风格，即使你会有不同的做法。
- 如果你注意到无关的死代码，提一下 — 不要删除它。

当你的修改产生孤立的代码时：

- 删除你的修改**造成**的不再使用的导入/变量/函数。
- 除非被要求，否则不要删除预先存在的死代码。

检验标准：每个修改的行都应直接追溯到用户的需求。

## 4. 目标驱动执行

定义成功标准。循环直到验证通过。

将任务转化为可验证的目标：

- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写重现它的测试，然后让它通过"
- "重构 X" → "确保测试在重构前后都通过"

对于多步骤任务，陈述简要计划：

1. [步骤] → 验证：[检查]
2. [步骤] → 验证：[检查]
3. [步骤] → 验证：[检查]

强大的成功标准让你能独立迭代。薄弱的标准（"让它工作"）需要不断澄清。

# BiSheng C（BSC）— 在编写任何 .cbs 代码前必须阅读

## 指针限定符语法（关键）

`_Owned` 和 `_Borrow` 是**指针限定符**，就像 `const`。它们放在 `*` **之后**，绝不能放在类型之前。

语法：`base_type *qualifier variable_name`

把它想象成 `const`：你写 `int *const p`，而不是 `const int* p` 来表示常量指针。
同样的规则：`int *_Owned p`，而不是 `_Owned int* p`。

### 正确

```c
char *_Owned msg = (char *_Owned)malloc(14);
int *_Owned p = (int *_Owned)malloc(sizeof(int));
const int *_Borrow r = &_Const x;
int *_Borrow mr = &_Mut y;
free((void *_Owned)p);
```

### 错误 — 导致编译错误："unknown type name '_Owned'"

```c
_Owned char* msg = malloc(14);     // 错误 — _Owned 不是类型
_Borrow int* r = &_Const x;       // 错误 — _Borrow 不是类型
```

**返回 BSC 代码前自我检查**：如果你写了 `_Owned T*` 或 `_Borrow T*`，重写为 `T *_Owned`。模式始终是 `T *_Owned`。

## 快速参考

- 文件：`.cbs`（源文件）、`.hbs`（头文件）。编译：`clang file.cbs -o output`
- `.c`/`.h` 文件可以用 `-x bsc`（或 `-xbsc`，两者都行）编译为 BSC：`clang -x bsc file.c -o output`
- 安全 API 需要 `#include "bishengc_safety.hbs"`
- 优先使用 `safe_malloc<T>(val)`（返回 `T *_Owned`，无需强制转换）和 `safe_free((void *_Owned)p)`
- Raw↔`_Owned` 直接 C 强制转换**即使在 `_Unsafe` 中也禁止**。使用内置函数：
  - Raw → `_Owned`：`__take_from_raw(raw_ptr)`（如果开启了可空性检查，则在空检查之后）
  - `_Owned` → raw：`__move_to_raw(owned_ptr)`（转移所有权）或 `(T *)&_Mut *owned_ptr`（仅借用，保留所有权）

## 代码验证

在编写或编辑任何 `.cbs`/`.hbs` 文件（或使用 `-x bsc` 编译的 `.c`/`.h`）后，运行上述部分的项目验证命令。在报告任务完成前修复所有编译器错误。

## LSP — 主动使用

BSC 感知的 clangd 会暴露所有权流和活跃范围。在对 `_Owned`/`_Borrow` 代码进行非平凡修改之前，在变量上 `hover` 以查看它在哪里被移动、借用或释放 — 不要从局部上下文猜测。要获取完整参考（可用性探查、已知 clangd 限制、回退到 Grep 的规则），加载 `/bsc` 并阅读 `references/lsp.md`。

## 何时加载其他技能

所有 BSC 语言主题都包含在单个 `/bsc` 技能中，它会路由到 `references/` 下按主题的文档。加载 `/bsc` 并阅读其路由表中命名的文档：

- 非平凡的 BSC 修改（新结构体、新的 `_Owned`/`_Borrow` 签名、跨所有权时间线的重构、`_Safe`/`_Unsafe` 边界决策）→ 在规划前阅读 `references/design.md`。
- 将 C 翻译/移植到 BSC → 在开始前阅读 `references/c-to-bsc-annotation-only.md`。仅仅更改文件扩展名不是翻译。
- 编译错误或调试陷阱 → 独立的 `/bsc-common-mistakes` 技能。

## 何时委托给 `bsc-planner` 代理

在规划需要阅读许多 `.cbs` 文件来理解所有权流的非平凡 BSC 修改时，使用 `bsc-planner` 子代理（通过 Agent 工具）——重构、新 API、跨模块影响分析，任何会消耗主上下文的任务。该代理是只读的，返回计划；主线程实现。不要委托给单文件编辑、拼写错误修复或已知函数的借用检查器错误——直接处理这些。

## 何时调用 `bsc-learn`（在会话结束时）

在非平凡的 BSC 编码会话之后——任何你修改或创建了 `.cbs`/`.hbs` 文件、遇到借用检查器或所有权错误、将 C 翻译为 BSC、或调试了析构函数/移动语义的会话——通过 Agent 工具调用 `bsc-learn`。

传递给它：
1. 你遇到的主要问题的简要总结（检查器拒绝了什么、哪些花了多次迭代、哪些令人惊讶）。
2. 覆盖此会话的 git 提交范围（例如 `HEAD~3..HEAD` 或特定的 SHA）。

该代理读取差异和现有技能文件，然后返回提议的技能改进文本。在应用任何编辑前将提议呈现给用户批准。不要自主应用编辑。

跳过 `bsc-learn` 的情况：只有注释编辑、单行拼写错误修复或没有 `.cbs` 修改的会话。
